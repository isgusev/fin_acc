# fin_acc — учёт личных финансов

Многопользовательское веб-приложение: счета, операции (доход / расход / перевод), планирование
доходов и расходов, автоматический расчёт плановой зарплаты с авансом и прогрессивным НДФЛ.

**Стек:** Python 3.12 · FastAPI · Pydantic v2 · SQLAlchemy 2 · Alembic · PostgreSQL 16 ·
Jinja2 + обычный JS · Gunicorn + Uvicorn · pytest · ruff · mypy · pre-commit · Docker.

---

## 1. Как забрать проект и запустить локально

Нужны: Git, Docker Desktop, Python 3.12 (Anaconda подходит).

### 1.1. Клонирование

```bash
git clone https://github.com/isgusev/fin_acc.git
cd fin_acc
```

Или в PyCharm: **File → New → Project from Version Control** → URL
`https://github.com/isgusev/fin_acc.git`.

### 1.2. Окружение Python

Через Anaconda:

```bash
conda create -n fin_acc python=3.12 -y
conda activate fin_acc
pip install -e ".[dev]"
```

Или через venv: `python3.12 -m venv .venv && source .venv/bin/activate && pip install -e ".[dev]"`.

В PyCharm: **Settings → Project → Python Interpreter → Add Interpreter → Conda Environment →
Use existing → fin_acc**.

### 1.3. База данных и настройки

```bash
docker compose up -d db          # PostgreSQL на localhost:5434 (+ база fin_acc_test для тестов)
cp .env.example .env             # при желании впишите ADMIN_EMAIL / ADMIN_PASSWORD
alembic upgrade head             # создать таблицы и справочники
```

### 1.4. Запуск

```bash
uvicorn app.main:app --reload
```

Откройте http://127.0.0.1:8000 — зарегистрируйтесь. Документация API (только не в production):
http://127.0.0.1:8000/api/docs

Администратор создаётся одним из способов:
- задать `ADMIN_EMAIL` и `ADMIN_PASSWORD` в `.env` — создастся при старте, если админов ещё нет;
- или командой `python -m app.cli create-admin you@example.com` (пароль спросит в консоли;
  существующему пользователю просто выдаст роль администратора).

В PyCharm для запуска: **Run → Edit Configurations → + → FastAPI** (или Python, module
`uvicorn`, параметры `app.main:app --reload`), working directory — корень проекта.

Целиком в Docker (как на проде): `docker compose --profile app up --build` → http://127.0.0.1:8000
(в `.env` для этого режима поставьте `COOKIE_SECURE=false`, т.к. локально нет HTTPS —
переменная из `.env` перекрывает значение из Dockerfile).

### 1.5. Тесты и проверки

```bash
pytest                    # все тесты (нужна запущенная база из docker compose)
pytest --cov=app          # с покрытием
ruff check . && ruff format --check .
mypy app
pre-commit install        # один раз: проверки перед каждым коммитом
```

Тесты используют отдельную базу `fin_acc_test` (переменная `TEST_DATABASE_URL`) и никогда не
трогают рабочую. Те же проверки запускаются в GitHub Actions на каждый push (`.github/workflows/ci.yml`).

## 2. Деплой на Amvera

Стек полностью подходит: Amvera собирает приложение из `Dockerfile` по `amvera.yml`
(docker-compose там не используется), HTTPS выдаёт сама платформа.

1. **Создайте PostgreSQL** в Amvera («PostgreSQL» → «Создать базу данных»):
   - версия **16.x** (как локально и в CI), тариф не ниже «Начального», 1 реплика;
   - имя БД `finacc`, пользователь `finacc` (Amvera не допускает `_`; имя `postgres`
     зарезервировано), длинный случайный пароль **из латинских букв и цифр** — иначе
     спецсимволы придётся кодировать в `DATABASE_URL` (`@` → `%40`, `:` → `%3A`, `/` → `%2F`,
     `#` → `%23`);
   - доступ суперпользователя `postgres` — **не включать**, внешний домен для БД — **не создавать**;
   - на вкладке «Инфо» базы возьмите внутренний хост вида `amvera-<логин>-cnpg-<проект-БД>-rw`.
2. **Создайте приложение** (тариф «Начальный») и на вкладке «Репозиторий» привяжите GitHub
   `isgusev/fin_acc`, ветка `main` — каждый push в `main` запускает сборку и деплой.
   Для привязки создайте отдельный токен GitHub только на этот репозиторий.
3. **Переменные окружения** (раздел «Переменные», пароли — как «Секреты»):

   | Переменная        | Значение                                                                  |
   |-------------------|---------------------------------------------------------------------------|
   | `DATABASE_URL`    | `postgresql://finacc:<пароль>@amvera-<логин>-cnpg-<проект-БД>-rw:5432/finacc` (секрет) |
   | `ADMIN_EMAIL`     | ваш email                                                                 |
   | `ADMIN_PASSWORD`  | надёжный пароль (секрет); после первого входа можно удалить               |
   | `FORCE_HTTPS`     | `true`                                                                    |
   | `WEB_CONCURRENCY` | `1` на тарифе «Начальный» (по умолчанию 2)                                |

   `APP_ENV=production`, `COOKIE_SECURE=true`, `TRUSTED_PROXY_HOPS=1` заданы по умолчанию.
   Имена БД и пользователя приложение берёт только из `DATABASE_URL` — локальная база
   (`fin_acc` в docker-compose) от них не зависит.
4. Включите домен в разделе «Домены» (HTTPS-сертификат выдаётся автоматически) и запустите
   сборку. При старте контейнер сам выполняет `alembic upgrade head`, затем Gunicorn.
   Проверка: `https://<домен>/health` → `{"status":"ok"}`.
5. Дальше — «Чек-лист перед выкладкой» в разделе «Безопасность».

## 3. Модель данных

Служебные поля, которых не было в ТЗ, добавлены во все сущности: `id` (UUID; у справочников —
целое), `owner_id` (владелец данных), `created_at` / `updated_at` (системные дата внесения и
изменения — не путать с датой операции, которую вводит пользователь).

| Сущность | Поля из ТЗ | Добавлено |
|---|---|---|
| **Пользователь** | Имя/Псевдоним, Зарплата, Дата аванса, Дата зарплаты, Расчёт аванса | email (логин), хеш пароля, роль, активен, «сменить пароль», счётчик неудачных входов |
| **Счёт** | Наименование, Тип счёта, Регулярность пополнения, Сумма рег. пополнения, Кол-во месяцев до цели (пусто = бессрочно), Закрыт, Целевая сумма (фонды) | дата закрытия |
| **Операция со счётом** | id счёта, Дата, Наименование, Сумма, Категория, Тип операции, Связь с планом | **счёт-назначение** (для переводов), **комментарий** |
| **Планирование** | Плановая дата, Наименование, Сумма план, Сумма за вычетом налога, Налогообложение, Ставка налога, Сумма факт, Тип операции, Вид дохода, Источник финансирования, Соотнесение с операцией | признак «создано автоматически» |
| **Праздничные даты** | Дата от, Дата до, Наименование | — |
| **Расчёт налогов** | Сумма дохода от, Сумма дохода до (пусто = без границы), Налоговая ставка | — |

**Справочники** (общие, правит только администратор): типы счетов, типы операций, виды дохода,
категории расходов.
У «системных» записей есть код, на который опирается логика, — их можно переименовать,
но нельзя удалить. Шкала налогов и праздники — тоже общие и только для администратора.

## 4. Бизнес-правила

- **Баланс счёта** не хранится, а считается из операций:
  `доходы − расходы − исходящие переводы + входящие переводы`. Поэтому правка операций
  в прошлом автоматически даёт верные остатки. Баланс может уходить в минус.
- **Тип «Перевод»** добавлен к типам операций: одна запись со счётом-источником и
  счётом-назначением (они обязаны различаться).
- Суммы доходов, расходов и переводов — строго больше 0 (проверка и в API, и в БД).
- **Доход** всегда зачисляется на счёт «Нераспределённый доход» (создаётся при регистрации)
  и обязательно связан с записью планирования с типом «Доход».
- **Расход** требует наименование; может быть связан с планом-расходом.
- Не больше **одного открытого** счёта типов «Текущий», «Накопления», «Нераспределённый доход»
  на пользователя. Наименования открытых счетов пользователя уникальны.
- Нельзя удалить счёт, по которому есть хоть одна операция. Закрыть — только при нулевом остатке.
  Операции по закрытому счёту нельзя создавать и менять.
- **«Открыть заново»** (фонды): новый счёт-фонд с тем же именем → перевод остатка → закрытие старого.
- **Категория** указывается только у расходов (из справочника); для расходов со счёта
  «Текущий» обязательна. Отключённая категория остаётся у старых операций.
- **Целевая сумма фонда**: сумма пополнения рассчитывается автоматически —
  целевая сумма ÷ (месяцев до цели ÷ месяцев в периоде): 15 000 за 9 месяцев ежеквартально →
  5 000 в квартал. Нужны «месяцев до цели» и регулярность.
- **История пополнений** (ежемесячные траты, фонды): за последние 6 месяцев, строка на период
  регулярности — ежемесячно: 6 месяцев; ежеквартально: кварталы, задевающие эти 6 месяцев
  (в октябре — II, III, IV); ежегодно: годы; еженедельно — 6 месяцев с нормой
  «сумма × дней в месяце ÷ 7». Шкала — пополнено за период ÷ «Сумма пополнения».
  Перенос остатка при «Открыть заново» не учитывается.
- **Сводка месяца** вверху страниц «Ежемесячные траты» и «Фонды»: открытые счета, баланс и
  прогресс пополнения в текущем месяце; «Итого» — общий баланс и сумма пополнений из суммы
  ожидаемых. Ожидаемое за месяц — по действующему плану, приведённому к месяцу
  (ежеквартальный — треть, ежегодный — 1/12, еженедельный — × дней месяца ÷ 7). Счета без
  плана в итоговый процент не входят.
- **История плана пополнения**: при изменении суммы или регулярности счёта указывается месяц,
  с которого действует новый план («Изменение плана пополнения действует с», по умолчанию —
  текущий месяц). Периоды до него в истории пополнений считаются по прежнему плану
  (сентябрь: 20 000 из 20 000 — 100 %), а в строке смены плана видна пометка
  «План с 01.10.2026: 25 000 ₽ ежемесячно (было 20 000 ₽ ежемесячно)». Если регулярность
  меняли, прежний план пересчитывается в длину строки (ежемесячные 20 000 в квартале — 60 000).
- **«Сумма факт»** плана = сумма связанных с ним операций.

### Расчёт плановой зарплаты

Кнопка «Рассчитать плановую зарплату с <дата>» создаёт выплаты до конца года этой даты.
Нужно заполнить в профиле «Зарплату» и «Дату зарплаты» (числа месяца; 31 → последний день
короткого месяца). Рабочие дни — пн–пт без праздников.

- Без «Даты аванса» — одна выплата в месяц на всю зарплату.
- С «Датой аванса» каждый месяц W делится на две выплаты:
  - **аванс** за W = зарплата ÷ рабочих дней W × рабочих дней W с 1-го по «Расчёт аванса»
    включительно — выплачивается в месяце W на «Дату аванса»;
  - **зарплата** за W = зарплата ÷ рабочих дней W × оставшихся рабочих дней W —
    выплачивается на «Дату зарплаты»: **в следующем месяце**, если она раньше «Даты аванса»
    (аванс 25-го, зарплата 10-го), иначе в том же месяце.
  - Поэтому при расчёте с начала года 10 января придёт остаток за декабрь прошлого года,
    а остаток за декабрь — 10 января следующего года (и попадёт в налоговую базу того года).
  - Пример, ноябрь 2026, зарплата 100 000, «Расчёт аванса» = 15: рабочих дней 21 − 1 (04.11) = 20,
    до 15-го 10 − 1 = 9 → аванс 25.11 = 45 000, зарплата 10.12 = 55 000.
- Проверки профиля: «Расчёт аванса» обязателен при указанной «Дате аванса» и не может быть
  позже неё; «Дата аванса» и «Дата зарплаты» должны различаться.
- **Доход с начала года до начала учёта** — отдельное поле в блоке расчёта зарплаты
  (хранится для каждого года). На счета не зачисляется, а служит начальной базой
  прогрессивной шкалы; при изменении налоги плана за год пересчитываются.
- «Заменить» выключено — даты, где плановая зарплата уже есть, пропускаются;
  включено — существующие записи зарплаты в периоде пересоздаются (кроме уже связанных
  с фактическими операциями).
- **НДФЛ прогрессивный**: база — доход до начала учёта + сумма «Сумма план» всех предыдущих
  (по дате) записей года с видом «Зарплата» или «Премия». Часть суммы, попадающая в каждую ступень шкалы,
  облагается своей ставкой; в «Ставку налога» записывается наибольшая из применённых.
  При любом изменении зарплат/премий года налоги пересчитываются.
- Для «Премии» с налогообложением ставка тоже считается по шкале; для прочих видов
  дохода ставку вводит пользователь.

### Прогноз накоплений

Страница «Прогноз»: накопления на конец каждого месяца на 12 месяцев вперёд, нарастающим
итогом. Старт — текущий остаток на счетах «Накопления» («Нераспределённый доход» и «Текущий»
не учитываются). Каждый месяц: + плановые доходы после налога без факта; − отчисления в фонды
и на ежемесячные траты по их планам пополнения (приведённым к месяцу); − плановые расходы с
источником «Накопления» или без источника (расходы из фондов, ежемесячных трат и «Текущего»
покрываются этими счетами и не вычитаются). В текущем месяце — только то, что ещё не случилось:
просроченные планы без факта считаются предстоящими, отчисления — за вычетом уже сделанных.
Месяцы после последнего планового дохода отмечены. На главной — строка «Прогноз накоплений
на 31.12».

На главной рядом со сводным балансом — «Ближайшие запланированные траты»: плановые расходы
без факта (включая просроченные).

### Импорт выписки Т-Банка

«Импорт выписки» → вставьте текст выписки, скопированный из PDF Т-Банка → «Разобрать».
Откроется таблица **только списаний** (суммы — положительные): дата, сумма и описание из
банка не редактируются; наименование, счёт, категория, связь с планом и комментарий —
редактируются; ненужные строки удаляются. «Сохранить» (с подтверждением) создаёт расход на
каждую строку — все или ни одного: при ошибках ничего не пишется, ошибки видны в строках.

- **Подсказки** берутся из ваших прошлых импортированных операций (описание из банка
  хранится в операции): то же описание → наименование, счёт и категория как в прошлый раз;
  тот же магазин сети («Оплата в PYATEROCHKA …», другой адрес) → так же; иначе — счёт,
  использованный ранее для этой карты.
- **Повторный импорт** безопасен: строки, совпадающие с уже внесёнными (описание, дата
  операции, сумма), пропускаются.
- Разобранная выписка в БД не хранится — только итоговые операции.
- API: `POST /api/v1/import/tbank/parse` (`{"text": ...}`) и `POST /api/v1/import/save`
  (`{"rows": [...]}`); ошибки по строкам — в `error.rows`.

## 5. Безопасность

- Пароли — Argon2id; минимум 8 символов, буквы + цифры. Блокировка учётной записи на
  15 минут после 5 неудачных попыток + лимит попыток входа (20 за 5 минут) и регистрации
  (5 в час) с одного IP.
- Сессии хранятся на сервере (в cookie — случайный токен, в БД — только его SHA-256);
  cookie `HttpOnly`, `SameSite=Lax`, в production — `Secure` и префикс `__Host-`.
  Выход после 12 часов бездействия (не дольше 7 дней всего). Смена/сброс пароля завершают
  остальные сессии.
- Размер запроса ограничен 2 МБ; разбор выписки устойчив к «битому» вводу.
- Зависимости образа зафиксированы в `requirements.lock` (проверка: `pip-audit -r requirements.lock`).
- Автотест обходит все маршруты и проверяет, что без входа доступны только вход/регистрация,
  а раздел администратора — только администратору.
- CSRF: токен в каждой форме и в заголовке `X-CSRF-Token` для API (получить —
  `GET /api/v1/auth/csrf` или из ответа `/login`).
- Каждый запрос к данным фильтруется по владельцу; чужие записи выглядят как
  несуществующие (404). Администратор не видит финансовые данные пользователей.
- Только ORM / параметризованные запросы — без SQL-инъекций. Все входные данные проходят
  валидацию Pydantic и ограничения БД.
- Заголовки: CSP, `X-Frame-Options: DENY`, `nosniff`, HSTS в production.
- Секреты — только в переменных окружения; `.env` в `.gitignore`, pre-commit c gitleaks.

### Чек-лист перед выкладкой в интернет

1. В Amvera заданы `DATABASE_URL`, `FORCE_HTTPS=true`; включён домен с HTTPS.
   PostgreSQL **не** публикуется наружу (не создавайте для него внешний домен).
2. `ADMIN_PASSWORD` — длинный уникальный пароль; после первого входа переменную можно удалить.
3. Создайте свою учётную запись и **закройте регистрацию** (Администрирование → Настройки),
   если приложение не предназначено для посторонних.
4. Там же сверьте «Ваш IP по данным сервера» со своим внешним IP. Если не совпадает —
   подберите `TRUSTED_PROXY_HOPS` (число прокси перед приложением), иначе ограничение
   попыток входа будет работать неточно.
5. Включите резервное копирование БД в Amvera.

Остаточные риски (осознанно не закрыты): администратор, сбросив пароль пользователю, может
войти под ним — но при этом обязан сменить пароль, и пользователь не сможет войти, т.е.
вмешательство заметно; блокировку учётной записи после 5 ошибок может спровоцировать
посторонний (на 15 минут); двухфакторной аутентификации пока нет.

## 6. Формат ошибок API

```json
{"error": {"code": "VALIDATION_ERROR", "message": "Значение должно быть больше 0", "field": "amount"}}
```

Коды: `VALIDATION_ERROR` (422), `UNAUTHORIZED` (401), `FORBIDDEN` / `CSRF_ERROR` /
`PASSWORD_CHANGE_REQUIRED` (403), `NOT_FOUND` (404), `CONFLICT` (409),
`TOO_MANY_ATTEMPTS` (429), `INTERNAL_ERROR` (500). В веб-интерфейсе те же сообщения
показываются у полей формы или на странице ошибки.

```
  schemas.py       Pydantic-схемы (валидация)

  deps.py          текущий пользователь, админ, CSRF

  web/, templates/, static/   веб-интерфейс
  cli.py           python -m app.cli create-admin
migrations/        Alembic
tests/             pytest
```
